# WordPressブログ連携

読者向けは `https://yottabyte.jp/blog/`、記事管理は `https://cms.yottabyte.jp/wp-admin/`。旧mediaの投稿・画像は移行しません。

## 管理側

新規のWordPressに `wordpress-plugin/yottabyte-corporate-blog/` をZIPでアップロード・有効化します。このプラグインはcms.yottabyte.jpだけで動作します。通常の「投稿」と独立した「HPブログ」を使います。

1. 「HPブログ → 新規追加」でタイトル・本文・抜粋を入力します。
2. システム開発、業務改善・自動化、AI活用、HP制作からカテゴリーを1つ選択します。未選択ならシステム開発になります。
3. アイキャッチ画像は任意です。未設定ならカテゴリーに合う既存SVGを使います。本文・アイキャッチ画像はCMSのメディアにアップロードします。外部画像・埋め込みスクリプト・iframeは許可しません。
4. 「公開」または「更新」でHPの再生成を開始します。下書き・非公開・パスワード保護記事は読者向けAPIに含めません。公開を取り消すと次の正常なビルドでHPからも除きます。

管理用WordPressの通常フロントページはHPブログへ転送し、CMSにはnoindexを設定します。WordPress管理画面・ログイン・公開REST API・アップロード済み画像は使用できます。CMSの通常投稿や固定ページはHPに取り込みません。

## 自動公開

「HPブログ → HP公開連携」にGitHub fine-grained personal access tokenを設定します。対象は **YottaByte-jp/yottabyte_hpだけ**、権限は **Actions: Read and write** と自動付与のMetadata読み取りのみ。Contents書き込みなどは不要です。個人の広い権限のCLIトークンを流用しません。トークンはWordPressサーバーだけに保存し、Git、ログ、HTML、REST APIには出力しません。期限切れ前に同じ権限のトークンに更新します。

記事変更リクエストの終了時に、固定の `deploy-pages.yml` に `workflow_dispatch` を送ります。`main`以外のブランチや任意の宛先は指定できません。APIのHTTP204は「開始受け付け」で、公開完了を意味しません。結果はGitHub Actionsで確認します。接続エラーは管理画面に記録され、「HPへの反映を再試行」で再送できます。定期ポーリングはありません。

GitHub Pagesのビルドは公開読み取り専用の `/wp-json/yottabyte/v1/articles` を取得し、スキーマ・件数・画像URL・HTMLを検証します。旧media APIは一切呼びません。取得や検証・ビルドが失敗したら公開ジョブに進まず、現在公開中のHPを維持します。公開取り消しもビルド成功まで以前のHPに残るため、緊急時はGitHub Actionsの結果まで確認してください。

## 復旧・保守

- 自動反映に失敗したら、CMSの接続設定とGitHub Actionsの失敗理由を確認して再実行します。本文・画像の入力エラーなら記事側を修正します。
- CMS障害時も公開中の静的HPは表示できます。CMSが復旧するまで新しいデプロイは失敗させます。取得エラーを空記事として公開しません。
- プラグインを無効にすると公開APIと自動反映が止まります。記事データを自動削除するアンインストール処理はありません。GitHubの権限を止める場合は該当トークンを失効します。
- WordPressとプラグインの更新・サーバーバックアップは管理側で行います。新CMSと旧mediaは別インストール・別DBとし、旧mediaの削除時にCMSやHP・メール・ホスティング契約は削除しません。
- 初期状態は公開記事0件。ローカルのデザイン見本はWordPressに登録せず、本番に公開しません。
